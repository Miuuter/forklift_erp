# 0.2.0-rc.1 稳定性与恢复报告

## 结论

2026-07-15 至 2026-07-16 在本地 Linux/amd64 Docker 等价环境完成综合读取、库存写入、幂等竞争、附件、导入、租赁、批量事务和完整备份恢复测试。所有最终场景均为零非预期错误，应用和 MySQL 没有重启、OOM、死锁或连接池超时。

该结果证明当前代码和发布配置可进入真实 Synology 验收，但不代表 NAS 真机已经通过。目标 NAS 的 CPU 架构、磁盘、网络、DSM 反向代理和独立备份存储仍需现场验证。

- 付款幂等 C25：同一付款请求 25 路并发全部返回同一流水；同一冲销再以 25 路并发收敛到同一反向流水，50/50 请求成功，p95 约 104 ms。
- 库存 C10：9,410 次操作，包含 3,760 次入库、3,760 次出库和 945 次跨仓 FIFO 调拨；零错误、零死锁，整体 p95 约 61.7 ms。
- 附件 C25 / 30 秒：49,562 次 PDF 预览/下载，零错误，1,651.6 req/s，p95 24.7 ms。
- 重复导入确认 C25：只有一个 `READY → IMPORTING` 事务胜出，最终状态 `COMPLETED`，没有重复导入行。
- 租赁补账 C25：并发刷新成功，没有重复账期，最后归还成功。
- 批量事务 C10：采购批收货、维修批完成、盘点批完成和盘点草稿批删除均只有一个竞争事务胜出；其余请求按预期发生版本冲突，业务事实保持全成全败。

- 登录：122.5 req/s，p95 96.2 ms。

## 压测中发现并修复的问题

### FIFO 调拨死锁

原实现对 FIFO 索引范围直接加悲观锁。相邻配件同时在源批次更新并向目标仓插入批次时，MySQL next-key gap lock 可形成环并报 1213。

修复为先读取候选批次主键，再按主键精确锁定。新增 12 个相邻配件并发调拨的 MySQL 回归测试；最终 945 次跨仓调拨零死锁。

### 日对账

原历史窗口 SQL 在约 23,123 条流水上 `EXPLAIN ANALYZE` 约 286 ms。改为余额驱动、按索引查询最近流水并聚合当日变化，候选 SQL 约 7.5 ms；V45 增加报表覆盖索引。

### 财务统计

原统计会把多个事实源的大量宽记录写入临时结果后再次聚合。当前实现先在数据库按月聚合两个事实源并 `UNION ALL`，只查询一次五年月度结果；当前年度月表和年度汇总在 Java 中复用该结果。

## 资源稳定性

最终 C50 五分钟运行期间：

- 应用峰值约 805 MiB / 1536 MiB；结束后约 819 MiB，重启 0，OOM=false。
- MySQL 峰值约 624 MiB / 768 MiB；重启 0，OOM=false。
- 日志未发现真实 `ERROR`、死锁、超时或连接池耗尽。日志中出现的 `ExitOnOutOfMemoryError` 是 JVM 启动参数，不是 OOM 事件。

## 备份恢复

备份包含压缩 MySQL dump、完整 uploads、元数据和 SHA-256 校验。空白隔离环境恢复后验证：

- 41 张表，Flyway V45；
- 1,450 台车辆、445 个客户、1,290 张出库订单、25 项配件；
- 1 个活动附件及对应文件，uploads 共 2 个文件；
- 应用健康、构建版本、登录、库存 API 和附件下载。

`restore-drill.sh` 已自动化上述数据库、文件和应用级核验。由于 Windows 本地安全策略不允许把 Docker socket 挂载给第三方容器，本轮使用同等的直接 Docker CLI 隔离流程完成验证；目标 Synology 应按脚本原样执行。
